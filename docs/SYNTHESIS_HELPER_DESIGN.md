# Synthesis helper: design and spike record (2026-10-19)

Status: **Stage 0 (the spike) in progress; no application code; Stage 1 is not authorized until this note records a GO.** The last item of Phase 4 of the suite roadmap. The approved plan is rev 3 (kept with the session's plan file); this note is its durable record and takes the results as the spike runs.

## What it is, and what it is never claimed to be

Given a target molecule, an **optional external planner** proposes multi-step routes; OpenChem adds its own annotations to every molecule in a route. Standing rules: claims are measured, not asserted; "measured, not shipped" is an accepted outcome; **"no route found within the configured search limits" is a valid answer**; **a returned route is a hypothesis**, never a validated or feasible synthesis. A policy probability is the planner's number and not a measured chance a reaction works; a route score ranks, it does not predict feasibility; "in stock" is a match to a catalogue snapshot, not availability or legality to sell.

## Decisions (Alex, 2026-10-19)

1. **First planner to spike: AiZynthFinder.** Not committed to shipping it: if licence, Windows install or quality fails, the spike records NO-GO and names the next candidate (Syntheseus, or a small in-house RDKit/rdchiral template planner).
2. **Locate-only install**: the app never fetches anything (as Psi4). A download button is a later stage with pinned URLs and checksums, if ever.
3. **Regulated targets: routes are shown with an alert, with one exception.** No planning starts for a target matched to a **CWC Schedule 1** entry (the shipped `cwc-schedule-1` ruleset); the refusal names the reason. DEA listings, CWC Schedules 2 and 3 and everything else are alert-only.

## What was verified against the source

* **AiZynthFinder 4.4.1** (`pyproject.toml`, master, fetched 2026-10-19): Python `>=3.10,<3.13`; `numpy <2.0.0`; `onnxruntime ^1.23.0` required; TensorFlow only in the optional `tf` extra; console scripts `aizynthcli`, `aizynthapp`, `download_public_data`, `smiles2stock`, `cat_aizynth_output`. **The user's planner environment is therefore a separate Python from OpenChem's.**
* **No random-seed setting** appears in the README; the search settings include `max_transforms`, `iteration_limit`, `time_limit` (default 120 s) and `return_first`. The noise-floor design (an `iteration_limit` budget, repeated identical runs) follows.
* **In this repository:** `chem/isotopes.py` `same_structure` exists (merged); `RegulatoryEngine.screen(mol, jurisdictions, include_near_misses, as_of)` returns a `ScreeningReport` whose findings carry `ruleset_id` and `rule_id`, and the Schedule 1 ruleset id is `cwc-schedule-1`.
* **Gaps in the first plan, found by reading the code, and how the plan closes them:**
  * **The shared regulatory engine includes user rulesets** (`calculator._shared_engine()` calls `load_all()` with `include_user=True`, and `add_ruleset` honours `supersedes`), so a user file could supersede `cwc-schedule-1`. **Measured when the gate was built (slice 2, 2026-10-20): this is not live in the code as it stands.** `_shared_engine` builds `RegulatoryEngine(rulesets)` from a list, which neither applies `supersedes` nor drops a ruleset with a repeated id, so a user file with the id `cwc-schedule-1` sits BESIDE the shipped one (two rulesets, both screened) and `supersedes` does nothing; only `add_ruleset`, which that path does not call, would retire it. The gate does not rely on that staying so. **The gate builds its own engine from `load_all(include_user=False)`** and, if `cwc-schedule-1` is missing, has load problems or screening raises, reports `unscreened` and plans nothing. The ruleset's own `known_limitations` (ricin and saxitoxin not encoded; size limits over-report and never under-report; "corresponding alkylated salts" not matched) travel with every refusal: the gate is a list match, not a guarantee.
  * **The reaction-prediction plugin cannot reach a service** (top-level `plugins/reaction_prediction/`, narrow `PluginContext` namespaces only). Stage 1 adds a narrow `context.synthesis` handle, modelled on `PluginCalculations`.
  * **Nothing draws a reaction**, and `ui/` may not import RDKit. Stage 1 adds a `chem/` reaction-SVG function.
  * The bridge's service-run class (`PREVIEW_ONLY` exists in `domain/calculation_bridge.py`) is checked again when the assistant tool is built.

### What the AiZynthFinder paper itself reports (Genheden et al., J. Cheminform. 2020, 12, 70, DOI 10.1186/s13321-020-00472-1; PMC7672904, open access, read from the full text)

The numbers are for the 2020 software and policy; the current ONNX policy and 4.4.1 are not the system measured there. ### 0c. What the planner supplies, field by field (seven real targets, 100 iterations, ZINC stock and USPTO policy and filter; raw output in `benchmarks/synthesis/fixtures/`)

* **Per route:** a tree of molecule and reaction nodes; one score, `state score` (the paper's warning applies: it ranks the search's states and is "rather indiscriminate" about route quality).
* **Per molecule node:** `smiles`, `in_stock`, `is_chemical`, `hide`. Stock status exists for every node.
* **Per reaction node:** a `smiles` that is the **template** fragment (product >> reactants, partly mapped), and a `metadata` block with **`mapped_reaction_smiles`, the whole reaction of the real molecules with atom maps and stereo (present on 104 of 104 steps seen)**, `policy_probability` and its rank, `policy_name`, `template` (retro SMARTS), `template_code`, `template_hash`, `library_occurence` and `classification` (the 0.0 "Unrecognized" in every case seen). **No conditions, no yields, no reagents or solvents.** Atoms that only the reactants carry (a leaving group, the other half of a reagent) get new map numbers on the right and nothing on the left.
* **Search statistics:** solved flag, number of routes, number of solved routes, nodes, first-solution iteration and time, search time, the precursors in and out of stock, `profiling.iterations` and the policy call counts. **There is no field that says why the search stopped**: a stop at the iteration limit has to be read from `iterations == limit`, one at the time limit from `search_time >= limit`, and anything else is `unknown`. `build_routes` returns fewer routes than the tree holds (12 of 46 for aspirin).
* **No random seed**, as the README implies. Observed run to run with identical configuration: the solved flag, the top score and the solved-route count were the same every time (racemic ibuprofen unsolved four times out of four, (S)-ibuprofen solved three of three with 28 solved routes each time), while **the tree size and route count varied** (racemic ibuprofen: 131, 144, 144 and 148 routes, 537 to 550 nodes, 14 to 18 s) and the time varied by about 20%.
* **Outcomes that look like chemistry and are not to be read as such:** aspirin from salicylic acid and acetic anhydride, paracetamol, caffeine and (S)-ibuprofen are solved in **one step** from stock; racemic ibuprofen is **not solved at 100 iterations** while its (S) form is (the stock holds the (S) ester); sildenafil is solved in three steps; strychnine is unsolved, and its five returned routes are one bare target and four single steps (bromination) into a precursor that is not in stock (**the planner returns unsolved routes too: a route is not a solved route, and the parser decides which become routes**; corrected 2026-10-20, this note first said the tree was the bare target alone). A solved route here means every leaf is in a 2020 ZINC snapshot.

### 0d. The route validator (`benchmarks/synthesis/route_validator.py`, 16 tests, 16 of 16 mutations killed) (production copy: `chem/route_validation.py`, slice 6)

Separate outcomes, never one score: molecules parse; reactions parse **and their sides are the molecule nodes they connect** (a consistency check the first plan did not have, added because the planner's route is two parallel representations); mapping `complete` / `partial` / `absent`; **atom conservation only where the mapping is complete, otherwise `not_assessable`**; stock `all_in_stock` / `some_not_in_stock` / `not_provided`; and a list of what the planner did not supply. The conservation rule is fixed: every mapped atom of the product side has exactly one same-element partner on the reactant side; unpartnered reactant atoms are permitted and counted; charge and hydrogen counts are not compared. Nothing is repaired or invented. On the **60 reaction-bearing routes in the fixtures every one validates**, which says the planner's own bookkeeping is consistent (not that the chemistry is right); the checks are shown able to fail by the synthetic mutations (a parse failure, a sides-and-nodes mismatch, a flipped stereocentre, a stripped or partial mapping, a changed element, a missing partner, a missing stock flag).

### 0e. The quality protocol: what the reading changes, and what is proposed

Read from the PaRoutes paper (Genheden and Bjerrum, Digital Discovery 2022, 1, 527; DOI 10.1039/D2DD00015F; in the library as `genheden2022_paroutes.pdf`):

* **Route sets.** Two sets of **10,000 reference routes** from USPTO, set-n1 (one route per patent) and set-n5 (up to five), at most 10 reactions deep, chosen as the most diverse and **checked so that no route has a leaf that is an intermediate in another**. **The stock is the leaves of the reference routes** (13,633 and 13,783 molecules), by design: a ZINC-sized stock "could mask subtle differences between search algorithms" and its snapshot is arbitrary.
* **Metrics proposed there:** solved targets; **top-1, top-5 and top-10 route accuracy by tree edit distance** to the reference route (ranked by a recursive route score with arbitrary reaction costs, so ties are common); and a diversity count. The paper shows why accuracy is a harsh measure: **for about 45% of targets the top-1 route is shorter than the reference, and the leaf overlap is 0.63 to 0.68 while the exact route is recovered for only about 1 in 5**, so a miss is often an alternative route, not a wrong one.
* **Their numbers (the benchmark's own one-step model, trained on USPTO with the reference reactions removed; 500 iterations, no time limit, no filter, single CPU):** MCTS on set-n1 solved **9,714 of 10,000**, search time 303 s and first solution 8.6 s on average, **top-1 0.20, top-5 0.55, top-10 0.61**; on set-n5 solved 9,676, top-1 0.09, top-10 0.42.
* **The contamination finding.** The paper states that a one-step model "trained on the entirety of the USPTO dataset ... was trained on reactions found in the reference routes, making it biased", and using it is "a mix of neural network recommendations and what amounts to literature-lookup". **The public ONNX models AiZynthFinder installs are described only as the USPTO models, and no record says the reference reactions were excluded**, so on PaRoutes targets they are probably in the contaminated class. Consequences, all for the preregistration: (1) a high recovery rate with the public model **is not evidence that the planner generalises**; it is evidence it reproduces patent chemistry it was trained on; (2) a rate **below** the published 0.61 would be a red flag; (3) the claim that can be made is "returns routes that include known patent routes at a literature-consistent rate", never "proposes feasible routes for new targets"; (4) a clean measurement needs either the PaRoutes-excluded model (`uspto_keras_model.hdf5` in Zenodo 7341155, 275 MB, **Keras, so TensorFlow and the NumPy conflict**, and whether it excludes the reference reactions is not stated on the record) or a reference set that is not USPTO.
* **Search budget and noise.** The paper's budget is 500 iterations with no time limit; the spike's searches at 100 iterations took 2 to 16 s, so **500 iterations is affordable** (an hour or two for a few hundred targets in one warm process). Run-to-run variation is real in tree size and route count and absent in the solved flag and top score on the targets tried.

**Proposed protocol and thresholds (approved by Alex 2026-10-19; frozen in `benchmarks/synthesis/PREREGISTRATION.md`)** (the same pattern as proton affinity and bond dissociation):

* **Targets:** a fixed random draw (seed written in the preregistration) of **300 targets from set-n1**; **stock: the set-n1 stock (the reference leaves)**, loaded as a text stock; **500 iterations, `time_limit` 1,800 s as a safety net only**, `max_transforms` 6, the USPTO policy with the filter, the public ONNX models; one warm process per run.
* **Claim 1, a route was returned (solved with the set stock):** PASS at **at least 0.90** of targets, PARTIAL 0.80 to 0.90, NO-GO below 0.80. (Published 0.971 with the benchmark's own model.)
* **Claim 2, the reference route is among the top 10 returned routes** (exact reaction-set match after removing atom maps, stereo kept; "top" by the planner's own order): PASS at **at least 0.50**, PARTIAL 0.35 to 0.50, NO-GO below 0.35. (Published 0.61 by tree edit distance with an uncontaminated model; the stricter exact-match rule is expected to read lower and a contaminated model higher; **the result is reported with both caveats and never described as generalisation**.)
* **Validity:** among the returned top-1 routes, the fraction **fully validated by the validator** (outcomes 1 to 4) at **at least 0.95** (PASS), PARTIAL down to 0.80, NO-GO below; routes that are `not_assessable` are counted separately and never as valid.
* **Stability:** 20 targets drawn before the run, each run three times; the **solved flag must be identical in at least 19 of 20**; route count and first-solution time are reported as the noise floor.
* **Claim 3, feasibility:** not measured, never reported.
* **Verdict:** GO needs all four PASS; any NO-GO is a NO-GO; otherwise PARTIAL with what works named and Alex's decision. **Resources are reported, not graded** (peak memory 5.3 GB, 1.7 GB on disk, about 16 s to start) but they are part of what a user is told before installing.
* **Why these numbers:** 0.90 sits below the published 0.971 by the margin a different model, a text stock and a Windows build might cost; 0.50 sits 0.11 below the published 0.61 for the stricter match; the validity and stability bars are set at what the fixtures already show (60 of 60 routes valid and a stable solved flag).
* **Not run until Alex says so:** 300 targets at 500 iterations is hours of CPU. The set-n1 route file, targets and stock (about 65 MB) were downloaded on 2026-10-19 with his go and checked against the record's MD5s.

### 0e, preregistered (2026-10-19): `benchmarks/synthesis/PREREGISTRATION.md`

Alex approved the thresholds as proposed above and the PaRoutes download; the preregistration freezes them with the runner. **Four things the downloaded data changed from the proposal** (each is in the preregistration, with the reason):

* **The file is ordered by the paper's greedy most-diverse selection**, so its head is the most atypical set: the first three targets have reference routes 8, 8 and 9 reactions deep (median 3, only 1% deeper than 6). The 300 targets are therefore a **seeded random draw** (seed 20261019), not the first 300, and the three the spike searched are excluded from it.
* **`max_transforms` 10, not 6**: the reference routes go up to 10 deep, and the default of 6 makes 1% of them unreachable by construction.
* **No filter policy**: the published numbers describe a search without one, and the three seen targets were identical with and without it.
* **The stock is a text file of InChI keys the planner computes**, not SMILES: 13,432 SMILES become 13,414 distinct keys (the paper says 13,633 leaves; the file holds 13,432, and equals the set of the reference routes' leaves exactly). With this stock the planner's peak memory is **about 0.8 to 0.9 GB**, against 5.3 GB with the ZINC stock: **the 5.3 GB is the stock's size, not the planner's**, which a user choosing a catalogue should be told.

On the three benchmark targets seen (indices 0 to 2) at 500 iterations the planner solved one of three, in 22 to 32 s of search each (about 30 s per process including start-up).

## After the result: the literature read, and a protocol difference it found (2026-10-20)

Alex supplied eight papers after the result was written (all registered in `docs/sources.toml`: `torrenperaire2024`, `maziarz2025syntheseus`, `saigiridharan2024aizynthfinder4`, `li2024retrobleu`, `genheden2021ted`, `morgunov2025retrocast`, `guo2026routeevaluation`, `armstrong2026synthex`). **None of this changes the verdict, which stands as measured under the frozen protocol.** It changes what the number can be taken to mean, and it corrects two sentences of the preregistration (which is not edited; this is the correction).

* **What "found" means in PaRoutes' own script.** `analysis/route_quality.py` of the PaRoutes repository (read 2026-10-20) counts a reference route as found only when the tree edit distance to a predicted route is below 1e-6, takes the top-k by rank, does no deduplication and leaves unsolved routes in the ranking. So the published top-n is an exact-match count, and **the preregistration's sentence that our exact-reaction-set rule is "stricter than the paper's tree edit distance, which gives credit for similar routes" is wrong for top-n accuracy** (the credit belongs to the similarity measure, not to the count). The two rules are of comparable strictness; ours keeps stereochemistry, theirs compares fingerprints.
* **Stereochemistry is ruled out as the cause.** Re-scoring all 300 saved first-run results with stereo ignored gives the same 0.157, 0.343 and 0.373 at ranks 1, 5 and 10 (60 of the 300 reference routes carry stereo marks; their recovery is 0.383 either way).
* **The route pool and its ranking differ, and they are configuration, not code.** Our runner called `build_routes()` with its defaults: at least 5 and at most 25 routes, `return_all` false, ranked by the default state score (`post_processing.min_routes`, `max_routes` and `all_routes`, `RouteSelectionArguments` in the installed 4.4.1, read from the package source). The median number of routes we returned was 11. The PaRoutes paper extracted a median of **273** routes per target with MCTS (its Table 2) and ranked them with Badowski's route cost with artificial leaf costs; AiZynthFinder 4.4.1 has both (`all_routes` and the `route cost` scorer). **Our recorded results hold only the routes returned, so recovery among solved routes that were not returned, or after a different ranking, cannot be recomputed from them. It needs a new search.** That this explains the gap is a hypothesis, not a finding.
* **Published reference points.** PaRoutes: top-1 0.20, top-5 0.55, top-10 0.61 for MCTS on set-n1, with a model that excludes the reference reactions. Torren-Peraire et al. (200 iterations, top-50 reactions added per iteration) report 23.7%, 56.5% and 60.7% for AiZynthFinder with a model trained on the reference-excluding USPTO-PaRoutes-1M set, and 61.8% at top-50 (their Table S7). Ours: **0.157, 0.343, 0.373** with a public model that is probably *not* reference-excluding. A model that has seen the reference reactions should score higher, not lower, so the preregistration's red flag (a rate below the published figure) stands and its likeliest causes are protocol ones. Morgunov and Batista summarise PaRoutes as showing 35 to 50% top-10 accuracy for models with over 97% stock-termination, a range that contains ours (their figure is a summary of other work, not traced).
* **Other evidence on what a PARTIAL here means.** The same papers say a solved route only means its leaves are in stock (Morgunov and Batista), that patent routes are a weak proxy for expert-validated ones (Guo et al., abstract; PaRoutes itself says other routes could be as effective as the reference), and that on 1,098 complex natural products AiZynthFinder solves 13.8% (Armstrong et al., the authors' own comparison, not reproduced). All support the narrowed wording ("valid, repeatable routes that often differ from the patent route"); none supports "known routes".

**Option 3 is therefore reframed, and the advice given on 2026-10-20 to defer it is revised.** That advice said a cleaner measurement would not change what ships; the protocol difference above means the PARTIAL itself may be partly a measurement artifact. Three variants, none run, each needing its own preregistration:

### Slice 3: the AiZynthFinder runner and parser (2026-10-20; `chem/aizynth_runner.py`, `chem/aizynth_planner.py`)

The planner is run as a separate program and AiZynthFinder is never imported into OpenChem's process. `run_planner(request, target, python=...)` starts the user's planner Python on `chem/aizynth_runner.py` with an argument array (no shell) and `-I`, sends one JSON request on stdin, reads one JSON document from stdout, and returns a `RouteSet`. Nothing calls it yet; slice 4's service does.

* **The contract, each point tested:** the configuration goes over stdin as a dictionary (a non-ASCII path survives as ASCII escapes); stdout carries one document and nothing else (the library's chatter is moved to stderr, and a document preceded by chatter is a failure); the status is in the document and the exit code must agree; the response is bounded (256 MB) and the search has a wall clock (the time limit plus a 600 s margin for a start-up measured at 16 to 18 s); either bound being passed, or `cancel` being set, kills the child; nothing retries and no limit is changed. Malformed JSON, an unsupported schema, a premature exit and a non-zero code beside a result are each `failed` with the child's last words (its stderr tail) in the reason; the planner's Python, the runner script, the policy model, the templates, the filter or the stock not being there is `unavailable` and says which, checked by the runner BEFORE the library is loaded because the library's own messages for them are poor.
* **Cancel leaves no process, measured on the real planner:** with the child seen alive by command line mid-run, a cancel at 4 s returned `cancelled` and nothing running `aizynth_runner.py` remained (the launcher and the real interpreter both carry that command line). It agrees with 0b: killing the launcher ends the real interpreter (a Windows job object).
* **Which of the planner's routes become routes (decided here).** The planner returns more than solved routes (the strychnine fixture: the bare target and four one-step routes into a precursor not in stock). A route is kept only if it has a reaction and every starting material is flagged in stock; the rest are counted in a limitation on the set ("Routes the planner returned that are not shown: ..."), and a search that returned only those is `no_route`. Sildenafil at 100 iterations: five returned, two kept. **The order is the planner's own**; re-ranking by the PaRoutes route score, and whether to ask for every solved route (`PlanRequest.all_routes`) rather than the default 5 to 25, wait for protocol 2 of the quality benchmark.
* **Nothing is invented:** a reaction SMILES, template id, policy name or probability the planner did not give (or gave out of range, or as a boolean) is `None`; a stock flag that is missing is not "in stock"; the planner's score is carried as its ranking number and `None` if absent. The route validator is not run here (`Route.validation` is `None` and the set says some routes have not been checked); moving it into `chem/` is slice 6.
* **Tests:** 85, of which 4 drive the real AiZynthFinder through the real runner when it is installed (skipped otherwise): the parser on all nine saved planner outputs, a stand-in child for every failure mode, the runner script with a stand-in library, and one exchange parsed by the host from the runner's own document.
